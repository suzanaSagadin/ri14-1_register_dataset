# RI XIV,1 Register Dataset

Ground truth for **person extraction and reconciliation** in historical digests,
derived from two public sources of the **Regesta Imperii** (RI):

* the digests (German: *Regesten*) of **RI XIV,1** (Maximilian I., 1493–1495, ed. Hermann
  Wiesflecker, Köln/Wien 1990), as exported by RI Online, and
* the printed **index of persons and places** to that volume (Angelika Schuh, *Register der
  Personen- und Ortsnamen 1493–1495*, Köln/Weimar/Wien 1996), from the editorial Word
  manuscript published in the RI Lab repository.

Every index entry that carries digest numbers becomes one entity with a frozen identifier.
Every digest lists the entities the index attaches to it. For every entity–digest link the
dataset also records the **mention string** in the digest text with character offsets, found
automatically and then reviewed link by link (see *Mention curation*). Because the index was compiled by the
editors of the digests themselves, the identity decisions ("Hg Albrecht von Bayern" in
digest 3135 is Albrecht IV. of Bayern-München) are specialist decisions made once,
consistently, across the whole volume.

## Files

| path | content |
|---|---|
| `data/entities.jsonl` | one entity per line: id, type (`person`, `place`, `other`), label in the index's own form, headword, sub-entry, source spellings (`variants`), alternative headings (`aliases`), digest ids, classification confidence |
| `data/digests.jsonl` | one digest per line: id, number, dates, place of issue, text, archival note, RI Online URL, scan URL, entity ids by type |
| `data/mentions.jsonl` | one line per entity–digest link (all types): the mention string, character offsets into the digest text, kind (direct / indirect), the finder's proposal and the curation verdict |
| `data/links.csv` | flat digest–entity table, all types |
| `data/splits/` | digest ids of the published catalogue (80 %) and test (20 %) partition, fixed seed |
| `raw/SOURCE.json` | provenance: source repository, commit, download date, LibreOffice version, SHA-256 of both input files |
| `stats.md` | counts, generated by the build |
| `curation/` | the reviewed decisions the build applies, `mention_fixes.jsonl` and `type_fixes.jsonl`, one row per link or entity with annotator and date, and the two instruction files that define the conventions |

### Identifiers

`RI14-1-E0071` = dataset `RI14-1`, entry number 71 in index order. Identifiers are neutral (they
say nothing about the type), assigned once, and must not be renumbered; corrections to an entity
keep its id. They carry no meaning outside this dataset; links to GND or Wikidata, when added,
are separate fields. Digest ids are the RI identifiers (`RI XIV,1 n. 2925`).

### Entity types

| type | subtype | meaning |
|---|---|---|
| person | individual | one human being, named or referred to by title |
| place | settlement, region, site | a location: town or village; landscape or land; building, castle, church, river, pass |
| other | family, group, institution, office, territory, property, event, object | a family or lineage; a collective (Bürger, Juden, Gesandte); a corporate body that acts (Regiment, Domkapitel, Stadt as party); an office without holder; a political unit (Hgtm, Gft, Btm); land, rights, revenues; a treaty, diet, battle; a movable thing |

Types were assigned in a two-pass model curation (see *Type curation*); the rule-based
parser's own guess is kept in `classification` for the record, `type_source` names who decided.

### Entity record (example)

```json
{
 "id": "RI14-1-E2458",
 "type": "person",
 "subtype": null,
 "label": "Liechtenstein, Paul von, Hofmarschall zu Innsbruck, Pfleger zu Thaur und Sarnthein",
 "headword": "Liechtenstein",
 "subentry": "Paul von, Hofmarschall zu Innsbruck, Pfleger zu Thaur und Sarnthein",
 "parent_place": null,
 "variants": [
  "Li(e)cht(t)enstain",
  "Lichtenstein",
  "Lichtenstain"
 ],
 "aliases": [
  "Innsbruck/Tirol, Marschall",
  "Sarnthein (Südtirol), Pfleger",
  "Thaur/Tirol, Pfleger"
 ],
 "digests": [
  "RI XIV,1 n. 39",
  "RI XIV,1 n. 40",
  "RI XIV,1 n. 84",
  "..."
 ],
 "classification": {
  "confidence": "high",
  "reason": "given name"
 },
 "type_source": null
}
```

`variants` are the source spellings the index prints in italics; `aliases` are other index
headings that redirect to this entry. Together they are the name forms a system may expect to
meet in the text.

### Mention record (example)

```json
{
 "digest_id": "RI XIV,1 n. 39",
 "entity_id": "RI14-1-P1177",
 "label": "Liechtenstein, Paul von, Hofmarschall zu Innsbruck, Pfleger zu Thaur und Sarnthein",
 "match": "exact",
 "text": "Paul von Liechtenstein",
 "start": 21,
 "end": 43,
 "occurrences": 1,
 "confidence": "high"
}
```

`text` is `digest.text[start:end]`. Every link was decided in two passes: an automatic
finder proposed a string (`auto_match`, `auto_text` keep its result), and a curation pass
confirmed, corrected or supplied the string, or declared the entity absent from the text
(`verdict`). `kind` is `direct` when the entity is named, `indirect` when it is referred to by
title, office or description only ("Kg von Frankreich" for Karl VIII., "Hofstaat der Kgin").
`source` names who decided. When the same string occurs more than once in a digest, the
occurrence meant is the one at `start`; `occurrences` gives the count.

Links with `verdict: absent` have no string: the index attaches the entity to the digest, but
the digest text as exported does not refer to it. Most of these are co-addressees of parallel
mandates, sources or witnesses that the printed volume names in the archival note or
commentary, which the export does not carry, or issue places that stand only in the editorial
header. A few are suspected index errors; the `note` field says so.

### Mention curation

The automatic pass was reviewed link by link, all 19,653 links, by **Claude Fable 5.1**
(model `claude-fable-5-1`, Anthropic), working in batches of 100 digests from
`curation/INSTRUCTIONS.md`, which fixes the span conventions. The model confirmed or
corrected the automatic string, supplied the string where the finder found none, marked
indirect references, or declared the entity absent from the text. Its decisions are in
`curation/mention_fixes.jsonl`, one row per link with verdict, annotator and date, and the
build applies them on top of the automatic pass (`python build.py --from mentions`). The
decisions were spot-checked by the dataset author; they are not an independent human
annotation. `stats.md` reports the verdicts and, as a by-product, the precision of the
automatic finder per match type (about 59 % for its best class, which is why every link was
reviewed rather than a sample). The model's notes on suspected index errors and on entities
whose type looks wrong are kept in the `note` field of the fix rows; they are the starting
point for the next curation pass on entity types.

### Type curation

The parser's person / place / other split was wrong for roughly a fifth of the entries
(things typed as persons, persons filed under a place or territory typed as "other"). Every
entry was therefore classified afresh by a language model from the index entry, up to three
digest excerpts around its curated mention strings, and the mention annotators' notes, following
`curation/INSTRUCTIONS_types.md`: a first pass over all 5,204 entries with **Claude Sonnet 5.5**,
and a second pass with **Claude Opus 5.5** over every entry the first pass did not decide with
high confidence, every "Stadt / Markt / Gemeinde / Dorf" sub-entry (with one firm rule for
consistency), and a random sample of 200 confident changes as a quality check. Decisions are in
`curation/type_fixes.jsonl` (entity id, type, subtype, confidence, note, annotator, date); the
build applies them in `src/curate_types.py`. `stats.md` reports the resulting distribution and
how often the second pass overruled the first.

Two conventions to know. "Stadt / Markt / Gemeinde" sub-entries under a place are the civic
community as a legal person (`institution`); the bare headword is the location. Jurisdiction
entries (Gericht, Landgericht, Vogtei, Amt, Pflege) are `territory`, `property` or `institution`
depending on how the digests use them, as a district, as a right held in fief or pledge, or as
a court that acts; the reviewer decided from the excerpts, and these subtypes are the least
consistent part of the typing. Person versus non-person, which matters for reconciliation, was
the focus of the pass.

### Split

`data/splits/catalogue_digests.txt` and `test_digests.txt` partition the digests that mention
at least one person, 80/20, shuffled with seed 20261006. The split is published so that results
are comparable: a reconciliation task derives its catalogue (persons occurring in catalogue
digests, with profiles built only from those digests) and its test items (persons in test
digests, "known" if in the catalogue, else "new") from these lists. `tools/make_reconciliation_task.py` derives those task files from this
dataset for the reconciliation use case; the use case repository ships the result.

## Building

```
python build.py
```

Requirements: Python 3.10+ (standard library only) and LibreOffice (`libreoffice` or `soffice`
on the PATH) for converting the Word index. The build downloads the two source files at the
commit recorded in `raw/SOURCE.json` (first run: current `main`), records checksums, parses,
joins, finds mention strings, writes the split, validates and writes `stats.md`. Every step is
deterministic. `python build.py --from parse_register` re-runs from a step;
`--force-download` fetches the current sources and re-pins the commit.

## What the ground truth is, and is not

* **Index coverage.** Persons the editor did not index are absent. The king himself ("KM") is
  not indexed as a person. Offices without a named holder ("Salzburg, Dompropst") are type
  `other`, not persons.
* **Mention strings were reviewed by a language model, not by two human annotators.** The
  span conventions are documented; disagreements with them are possible in coordinated name
  lists ("Paul und Reichard von Absperg" gives each brother only his given name) and in
  indirect references.
* **Volume 1 only.** The index does not link persons across RI XIV volumes. Adding volume 2
  would require matching its index by name.

## Curation status

The parser's own classification was rule based and is superseded by the type curation; its
decision stays in each entity's `classification` field for the record. Known gaps: 281 index
redirects whose target could not be identified, so an alias is missing from the target entity;
8 index entries without digest numbers, dropped; one index number absent from the RI Online
export (digest 519), link dropped; 926 links the curation marked absent from the digest text.
Corrections are made in the parser rules or in the curation files, never by hand in `data/`,
so that the build stays reproducible. The index's Word export occasionally lost a sub-entry
marker or wrapped an entry over several lines; the parser repairs the patterns observed in
this volume (see comments in `src/parse_register.py`).
